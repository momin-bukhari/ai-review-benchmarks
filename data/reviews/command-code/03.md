# Review: Batch queued deliveries

## Bug: Remainder batch is silently dropped — data loss

The batching loop `range(0, len(jobs) - batch_size + 1, batch_size)` only produces full batches. When `len(jobs)` is not a multiple of `batch_size`, the remaining jobs are never processed.

Example: 25 jobs with `batch_size=20`:
- `range(0, 6, 20)` → `[0]` — only one batch of 20, the last 5 jobs are skipped.
- `processed` returns 20 instead of 25.
- The 5 remaining deliveries stay as pending forever (until the next worker invocation, if ever).

**Fix:** Use `range(0, len(jobs), batch_size)` instead, which handles both full and partial batches:
```python
for start in range(0, len(jobs), batch_size):
    batch = jobs[start:start + batch_size]
    ...
```

This is a correctness bug that causes silent data loss under common conditions.

## Positive: executemany batching

Using `db.executemany()` for batch inserts and updates is a reasonable optimization to reduce per-statement overhead. The approach is sound — just the loop bounds are wrong.
