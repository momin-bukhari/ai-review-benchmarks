# Review: Retire the legacy delivery column

## Critical Risk: Dropping legacy_format breaks live workers at the elm site

The deployment evidence shows that at the **elm** site, `workers-17` (2 replicas) actively queries:
```sql
SELECT id, legacy_format FROM deliveries WHERE delivered_at IS NULL
```

This migration runs `ALTER TABLE deliveries DROP COLUMN legacy_format`. Once the migration executes, the `workers-17` polling query will fail with a "no such column" error, causing those 2 worker replicas at elm to crash or stop processing deliveries.

The **cedar** site only runs `workers-18` which queries `SELECT id, report` — it's unaffected.

## Recommendation: Gate the migration on worker upgrade

This migration should not run until all `workers-17` instances at elm have been upgraded to `workers-18` (or later). Options:
1. Upgrade elm workers first, then run the migration in a subsequent deploy.
2. Add a pre-migration check that verifies no active workers reference `legacy_format`.
3. Use an expand-and-contract pattern: first stop writing to the column, then stop reading, then drop it.

## Note on migration ordering

The migration file is numbered `002`, which will run after `001_initial.sql`. The migration system (`migrate()`) processes files in sorted order by number, so this will execute correctly on the next application startup. The concern is purely about the deployment ordering relative to worker upgrades.
