# Review: Page report history by scheduled time

## Bug: Cursor tiebreaker mismatch causes skipped/duplicated rows

The `WHERE` clause filters with `scheduled_at < ?` but the `ORDER BY` is `scheduled_at DESC, id DESC`. When two deliveries share the same `scheduled_at` value, the cursor only compares on `scheduled_at`, so the next page's `WHERE scheduled_at < X` will skip any rows with `scheduled_at = X` that should appear after the tiebreaker row.

Example: if deliveries at `scheduled_at=100` have ids 5 and 3, the first page might show `(id=5, scheduled_at=100)`. The cursor is `100`. The next page queries `WHERE scheduled_at < 100`, which skips `(id=3, scheduled_at=100)`.

**Fix:** Either include the id in the cursor comparison:
```python
query += " WHERE (scheduled_at, id) < (?, ?)"
params.extend([cursor_scheduled_at, cursor_id])
```
Or use `<=` with the id tiebreaker separately.

## Note: Cursor contract change

The cursor extraction changed from `rows[limit - 1][0]` (id) to `rows[limit - 1][2]` (scheduled_at). This is consistent with the ORDER BY change, but it changes the meaning of the opaque cursor value from an id to a timestamp. Existing clients holding an old-style cursor (an id) would get incorrect results if passed to the new version. This is acceptable if the cursor is truly opaque and not persisted across deploys, but worth noting.

## Positive: Correct ordering change

The intent to sort by `scheduled_at` rather than `id` is correct — it shows deliveries in the order they were meant to run, not the order they were inserted.
